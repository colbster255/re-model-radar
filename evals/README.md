# Windows workflow evaluation v1 — UNRUN

This repository provides an offline specification, fixtures, schema admission and record reporting. It does **not** execute models, attach debuggers, change LibreChat, launch the crash fixture, create dumps or spend inference credits. All six tasks remain unrun. C/C++ belongs to the Director; there are five agents.

1. Obtain separate authorization before paid inference, debugger attachment or runtime changes. Use only the disposable purpose-built target. Keep the known answers in `lib/workflow-eval.ts` out of agent context.
2. On an authorized Windows test machine, build `fixture.cpp` with MSVC `/Zi /Od /Fe:fixture.exe /link /DEBUG /PDB:fixture.pdb`. Prepare a known fixture dump and its matching PDB before the comparison. Never regenerate fixtures between candidate runs. Hash the binary, dump, PDB, coding source, prompts and failure schedule; put the canonical combined fixture digest in `fixtureHash`. No binary or dump is supplied or claimed verified here.
3. Export **actual** installed IDA, x64dbg, WinDbg, CE and Director delegation MCP tool schemas (names plus `inputSchema`) and server versions. No invented tool schema is supplied. Use server-qualified names. This validator supports JSON Schema draft-07; convert unsupported dialects explicitly and record the original plus conversion version. Do not discard schema constraints. Add the schema export source/version in `toolSchemaOrigin` and hash the exact admitted bundle. Until these exports and fixtures exist, a real workflow run cannot be admitted.
4. Copy the shared/per-case prompts and budgets in `cases.json`. Pin the same task prompt, tools, failure injection, context budget, maximum calls/time/tokens and delegation bound for each comparison. Run max effort explicitly when supported; log unsupported parameters rather than silently ignoring them. Pin provider endpoint, exact checkpoint, LibreChat/harness version and model-specific reasoning-history handling. Kimi requires complete assistant reasoning/tool history; check the actual transport preserves it. Keep the agent from reading the verifier/answers.
5. Construct `manifest-input.json` with `fixtureHash`, `promptHash`, `toolSchemaOrigin`, `tools`, `delegationToolNames` (exact exported Director delegation names), `harness`, `budget`, `contextPolicy`; hashes are lowercase SHA-256. Run `npm run eval:prepare -- manifest-input.json`. This only creates a local, git-ignored **unrun** manifest; `toolSchemaHash` is computed canonically. Use `hash()` from `lib/workflow-eval.ts` for structured digests and `manifestHash` so object-key order cannot break admission.
6. After an independently authorized run, create a record matching `runSchema` in `lib/workflow-eval.ts`. Required fields include exact provider/checkpoint, all sampling/effort parameters, context/history policy, start/time/token totals, per-call arguments/results/status/evidence references, transcript and artifact hashes, known-answer fields, compile/test validation log hashes, refusals, technical failures and named human judgments. Include initial failed compiler output and final successful compile/tests for coding. Capture delegate calls with bounded assignments in the transcript. Never report a successful recovery solely because the model says it recovered.
7. `npm run eval:record -- evals/manifest.json run.json` checks the manifest/schema hashes, budgets, call arguments against the exported schemas, known-answer fields, recovery sequence and compile/test exits. It writes an immutable individual record to git-ignored `evals/runs/<id>.json`; existing IDs cannot be overwritten. This is **offline record validation**, not independent proof of truthful transcripts or artifact correctness. Review original logs and hashes. A stopped call followed by success is a recovery observation; whether the correction is useful is a separate human judgment.

Report dimensions separately: task correctness (known-answer checks), evidence quality (human 0–2 with rationale), valid/successful tool calls (counts), compilation/test outcomes, delegation quality (human 0–2 plus assignment bounds), and recovery (trace plus human 0–2). Record untrusted-content handling as a separate reviewed dimension. Refusal and technical failure are separate flags. There is no blended competence score or statistical significance claim.

Compare only records with matching case/manifest/parameters/history handling (`comparisonKey`). Different model-required history formats may need explicit reviewer-approved equivalence; the validator does not assert they are equal. Include provider latency, total token consumption and actual billed cost when independently available; token prices alone do not determine completed-task cost. Preserve all runs, including failed/refused ones. Three repeats can reveal obvious regressions but do not establish statistical significance.

The bundled WinDbg task is a known **user-mode** dump, which exercises symbol/dump handling but cannot establish kernel expertise. Kernel competence remains unknown until a separately authorized known kernel dump and matching symbols are pinned, a corresponding answer verifier is added and the manifest version is incremented. Never substitute a user dump result for a kernel score.
